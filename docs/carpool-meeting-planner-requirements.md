# 配車さん 要件定義書

## 1. 目的

「配車さん」は、複数人で同じ目的地へ車移動する際に、各メンバーの住所、車を出せるメンバー、車ごとの乗車可能人数、目的地を入力すると、誰がどの車に乗るべきか、どこに何人集合すべきかを提案する。

手作業で発生しがちな「誰が誰を拾うか」「遠回りが大きすぎないか」「車の定員を超えていないか」「集合場所が偏っていないか」の判断を支援する。

## 2. 想定ユーザー

- 旅行、キャンプ、イベント、スポーツ、飲み会後の送迎などを調整する幹事
- 車を出せるメンバーと乗せてもらうメンバーが混在する小規模グループ
- LINE、Slack、Discordなどで集合案を共有したい人

## 3. スコープ

### 3.1 MVPで扱う範囲

- メンバー情報の入力
  - 名前
  - 出発地住所
  - 車を出せるか
  - 車を出せる場合の乗車可能人数
  - 同乗グループ（任意・数字指定）: 同じ番号のメンバーは必ず同じ車にする（ハード制約）。
    グループに車ありメンバーを含めると、そのメンバーの車に固定される。
  - 指定集合場所（任意・車ありメンバー向け）: 自宅とは別に「ここに集合して」を指定すると、
    その車は集合地点の自動選定を行わずこの場所を使う。
- 目的地の入力
- 最適化条件の選択
  - 総移動時間を短くする
  - 運転者の遠回りを小さくする
  - 車の台数を少なくする
- 結果表示
  - 車ごとの乗車メンバー
  - 車なしメンバーが公共交通機関で向かう集合地点
  - 想定ルート順
  - 各車の乗車人数
  - 各車の概算移動時間
  - 目的地への到着見込み
- 結果の共有
  - テキストでコピー
  - Google Mapsのルートリンク生成
  - 共有URL発行

### 3.2 MVPでは扱わない範囲

- リアルタイム交通状況の完全反映
- 有料道路料金、ガソリン代、駐車場代の精算
- メンバー本人によるログイン、出欠回答
- 複数目的地をまたぐ旅行行程管理
- ドライバーごとの運転可能時間や休憩制約
- チャットアプリ連携

## 4. ユースケース

### 4.1 幹事が集合案を作る

1. 幹事がツールを開く
2. 目的地を入力する
3. メンバー名と住所を入力する
4. 車を出せるメンバーにチェックを入れる
5. 各車の乗車可能人数を入力する
6. 最適化条件を選ぶ
7. 「計算する」を押す
8. ツールが乗車割り当てと集合/ピックアップ案を表示する
9. 幹事が結果をコピー、または共有URLを発行して共有する

### 4.2 結果を手動調整する

1. 幹事が計算結果を見る
2. 特定メンバーを別の車へ移動する
3. 集合場所を手動で変更する
4. 再計算する
5. 調整後の結果を共有する

## 5. 機能要件

### 5.1 メンバー入力

- メンバーを1人ずつ追加、編集、削除できる
- 各メンバーには以下を設定できる
  - 名前
  - 住所または地点名
  - 車あり/なし
  - 車ありの場合の乗車可能人数
- 乗車可能人数は「ドライバー本人を含む総定員」として扱う
- 住所未入力、名前未入力、定員不足などはエラー表示する

### 5.2 目的地入力

- 目的地住所または地点名を入力できる
- 目的地は1つとする
- 目的地が未入力の場合は計算できない

### 5.3 地点解決

- 入力された住所や地点名を緯度経度に変換する
- 候補が複数ある場合は候補選択を表示する
- 住所解決に失敗した場合は対象メンバーまたは目的地を明示する

### 5.4 距離・時間計算

- 各地点間の車移動時間、距離を取得する
- 取得できない場合は直線距離による概算にフォールバックする
- MVPでは距離よりも移動時間を優先して最適化する

### 5.5 割り当て計算

- 車を出せるメンバーを車両として扱う
- 車なしメンバーを可能な範囲でいずれかの車へ割り当てる
- 各車両の乗車人数は定員を超えない
- 全員を乗せられるだけの総定員がない場合も計算は続行する
- 総定員が不足する場合、乗車できないメンバーを「公共交通で目的地へ向かうメンバー」として表示する
- 車を出せるメンバーがいない場合は、全員を「公共交通で目的地へ向かうメンバー」として表示する
- 公共交通で目的地へ向かうメンバーには、現在地または入力地点から目的地までのGoogle Mapsリンクを生成する
- 総定員不足時は、何席不足しているかを明示する
- 目的関数は以下を組み合わせる
  - 全車両の総移動時間
  - ドライバーごとの遠回り時間
  - 使用車両台数
  - 車ごとの人数偏り
- 初期MVPでは厳密最適解でなく、実用的な近似解を許容する

### 5.6 集合方式

MVPでは「中間地点集合中心」を基本方式とする。

#### A. 中間集合地点優先

- 車なしメンバーは公共交通機関または徒歩で集合地点へ向かう
- 車ありメンバーは自宅から集合地点へ向かい、同乗者を乗せて目的地へ向かう
- 同じ車に割り当てられたメンバー群について、以下を考慮して集合地点を提案する
  - 車なしメンバーが公共交通機関で行きやすい
  - ドライバーの遠回りが大きすぎない
  - 目的地方面への進行を妨げにくい
  - 車で停車・合流しやすい
- MVPでは集合候補種別を「駅」「コンビニ」「駐車場」「任意キーワード」から選ぶ

#### B. 自宅ピックアップ補助

- 例外的に公共交通機関で集合地点へ向かうのが難しいメンバーがいる場合のみ、個別ピックアップ候補として扱う
- MVPでは補助機能扱いとし、初期実装の必須要件には含めない

### 5.7 結果表示

- 車ごとに以下を表示する
  - ドライバー名
  - 同乗者名
  - 推奨集合地点
  - 各メンバーの集合地点への移動手段目安
  - 集合地点から目的地までの推奨ルート
  - 目的地までの概算所要時間
  - ドライバーの単独移動と比べた追加時間
  - Google Mapsで開くリンク
- 車に乗れないメンバーがいる場合は、公共交通組として以下を表示する
  - メンバー名
  - 目的地まで公共交通で向かう案
  - Google Mapsで開くリンク
  - 車の席数が何席不足しているか
- 全体サマリーとして以下を表示する
  - 使用車両数
  - 全員の乗車可否
  - 公共交通で目的地へ向かう人数
  - 最長移動時間
  - 最も負担が大きいドライバー
  - 注意事項

### 5.8 手動調整

- 計算結果後にメンバーを別の車へ移動できる
- 移動後に定員超過があれば警告する
- 手動調整後にルート時間を再計算できる

### 5.9 共有

- 結果をプレーンテキストでコピーできる
- 結果を閲覧専用の共有URLとして発行できる
- 共有テキストには以下を含める
  - 目的地
  - 車ごとのメンバー
  - 集合地点
  - Google Mapsリンク
  - 注意事項
- 共有URLで表示する内容は以下に限定する
  - 目的地名または目的地の表示ラベル
  - 車ごとのドライバー名
- 車ごとの同乗者名
- 車ごとの集合地点名
- 集合地点のGoogle Mapsリンク
- 集合地点から目的地へのGoogle Mapsリンク
- 公共交通組のメンバー名
- 公共交通組の目的地までのGoogle Mapsリンク
- 幹事が入力したメモ
- 共有URLには以下を含めない
  - メンバーの出発地住所
  - メンバーの自宅緯度経度
  - 住所解決結果の詳細
  - 公共交通の詳細経路
- 共有URL発行時は、URLに含まれる情報を確認するモーダルを表示し、明示的な同意後に発行する
- 共有ページは閲覧専用とし、住所入力や再計算はできない
- MVPの共有URLはDBを使わず、共有表示に必要な最小限の結果データをURLフラグメントへ圧縮して埋め込む
- 共有URLの `#` 以降に入れたデータは通常HTTPリクエストとしてサーバーへ送信されない
- 共有URLはURLを知っている人が閲覧できるため、共有前に含まれる情報を明示する
- 共有URLの削除や有効期限はDBなしでは提供しない。必要になった場合のみ保存型共有へ拡張する

## 6. 非機能要件

### 6.1 使いやすさ

- スマートフォンで幹事が入力しやすいUIにする
- 入力項目は最小限にする
- 結果はLINEなどに貼りやすい文章で出力する
- 住所などの個人情報を扱うため、保存しない設計であることが分かるUIにする

### 6.2 パフォーマンス

- 10人、車3台程度なら数秒以内に結果を表示する
- MVPの想定上限は20人、車8台程度とする
- 外部APIの呼び出し回数を抑えるため、地点間距離の結果を一時キャッシュする

### 6.3 セキュリティ・プライバシー

- MVPではログインなしでも利用できる
- 入力データのうち、住所や緯度経度はサーバーに保存しない
- 住所、氏名、目的地は原則として実行中のブラウザメモリにのみ保持する
- LocalStorageには住所や氏名を保存しない
- 入力途中の自動復元が必要な場合も、住所などの個人情報は保存対象から除外する
- 共有URL発行時もサーバー保存は行わない
- 共有URLには、共有ページ表示に必要な最小限の結果データのみをURLフラグメントとして含める
- 住所情報を外部APIへ送信することをUI上で明示する
- Google Maps Platformへ送信される情報と、アプリ側で保存しない情報を区別して説明する
- 共有URLに含まれる情報と含まれない情報を発行前に明示する
- Next.jsのRoute HandlerはGoogle Maps Platformを呼び出すための一時的なプロキシとしてのみ使い、リクエスト内容を永続化しない
- Route Handlerでは住所、氏名、緯度経度、Google APIレスポンス詳細をアプリケーションログへ出力しない

### 6.4 可用性

- 外部地図APIが利用できない場合は、計算不可または直線距離概算であることを明示する
- APIキー未設定でもサンプルデータでUI確認できる

## 7. 推奨技術構成

### 7.1 初期実装

- アプリケーション: Next.js App Router + TypeScript
- Google API連携: Next.js Route Handler経由
- 共有URL: URLフラグメントに圧縮済み共有データを格納するDB不要方式
- 地図/住所解決: Google Maps Platform
- 距離行列: Google Maps PlatformのDistance Matrix APIまたはRoutes API
- 集合地点候補: Google Places API
- 最適化ロジック: TypeScriptで近似アルゴリズムを実装
- 状態保存: 原則メモリのみ。住所・氏名・目的地はLocalStorageへ保存しない
- APIキー管理: Google Maps Platformのサーバー用APIキーは環境変数で管理し、ブラウザへ露出しない
- ブラウザ用APIキー: Maps JavaScript APIを使う場合のみ利用し、HTTPリファラー制限と利用API制限を必ず設定する
- サーバー責務: Google APIプロキシ、入力検証、レスポンス整形のみ。DBや永続化は持たない

### 7.2 将来の高度化

- 最適化エンジン: Google OR-Tools
- 独立バックエンド: Node.js または Python FastAPI
- 永続化: SQLite、PostgreSQL、Supabaseなど
- 保存型共有URL: パスワード保護、期限設定、削除リンク、編集権限の追加

## 8. 最適化ロジックの初期方針

MVPでは次の段階的な近似アルゴリズムを採用する。

1. 全メンバーと目的地の地点情報を取得する
2. 各メンバーから目的地までの単独移動時間を計算する
3. 車ありメンバーをドライバー候補にする
4. 車なしメンバーについて、公共交通機関で到達しやすい集合候補を探索する
5. 各ドライバーと車なしメンバーの組み合わせについて、集合地点経由時の追加時間を概算する
6. 追加時間、公共交通アクセス、定員のバランスがよい組み合わせから割り当てる
7. 定員を超える場合は次善の車へ割り当てる
8. どの車にも割り当てられないメンバーは公共交通組へ入れる
9. 使用車両台数削減モードでは、少人数車両を統合できるか試す
10. 各車について集合地点から目的地までの車ルートを再計算する
11. 公共交通組について目的地までのGoogle Mapsリンクを生成する

将来的には、この問題を Capacitated Vehicle Routing Problem に近い形で扱い、OR-Toolsで制約付き最適化する。

## 12. 受け入れ基準

- 目的地、メンバー、車あり/なし、定員を入力できる
- 総定員不足を検知し、席数不足と公共交通組を表示できる
- 車がない場合でも全員を公共交通組として表示できる
- 車ごとのメンバー割り当てが表示される
- 定員を超える割り当てが生成されない
- 各車の集合地点、集合地点から目的地までのルート、概算移動時間が表示される
- 車なしメンバーは公共交通機関で集合地点へ向かう前提で表示される
- 車に乗れないメンバーは公共交通機関で目的地へ向かう前提で表示される
- 結果をテキストでコピーできる
- 共有URLを発行できる
- 共有URLを開くと、誰がどこに集まり、誰の車で目的地へ向かうかが閲覧できる
- 共有URLページにはメンバーの出発地住所が表示されない
- Google Mapsリンクを生成できる
- スマートフォン幅で主要操作が問題なく行える
- 住所、氏名、目的地がLocalStorageへ保存されない

## 13. 未確定事項・確認したいこと

1. 想定利用人数は最大何人程度か
2. 目的地は常に1つでよいか
3. 車の定員はドライバーを含む総人数でよいか
4. 高速道路を使う/使わないの条件指定が必要か
5. 到着時刻や出発可能時刻も考慮したいか
6. 公共交通機関の所要時間もGoogle Mapsで取得して考慮したいか
7. URLが長くなりすぎる場合、保存型共有URLへの拡張を許容するか
8. 料金精算機能は将来的にも不要か
9. まずはWebアプリでよいか、スマホアプリ化も視野に入れるか

## 14. MVP開発の推奨順序

1. 入力フォームと結果表示の静的UIを作る
2. サンプルデータで割り当てロジックを実装する
3. Google Mapsリンク生成を実装する
4. Next.js Route Handler経由で住所解決、集合地点候補、移動時間取得を接続する
5. 手動調整と再計算を追加する
6. 共有テキストコピーを追加する
7. 共有URL発行と閲覧専用ページを追加する
8. スマートフォン表示を調整する
